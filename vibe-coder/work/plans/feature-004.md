# Plan: Use Tailwind CSS for Still Cup custom template

> AI-managed only — humans do not edit this file.

## Summary

Full Tailwind v4 move for `still-cup`: utility classes in all theme PHP/JS templates; delete legacy `main.css` / `templates.css`; keep only a slim `overrides.css` for tokens, base, body hooks, and Woo/JS state that utilities cannot express.

## Goals

- Faster, AI-friendly front-end iteration in PHP templates
- Single source of truth for Still Cup colours, fonts, breakpoints, and content width
- Predictable enqueue: one built CSS artifact for the front end (plus optional small residual CSS if needed)
- No dependency on editing WooCommerce plugin files

## Recommended approach (decision)

| Option | Verdict |
|--------|---------|
| **A. Hybrid (chosen)** — Tailwind utilities + `@theme` tokens; keep `sc-*` component CSS for chrome/Woo where utilities alone are noisy | **Yes** — matches speed goal without a risky big-bang rewrite |
| B. Tailwind-only rewrite of all templates/CSS | No for this feature — high churn, easy visual regressions |
| C. CDN Play CDN / no build | No — not production-safe; bloated CSS; weak purge |

Stack choice:

- **Tailwind CSS v4** via `@tailwindcss/cli` (or Vite if the theme later gains JS bundling)
- Source: `assets/src/css/app.css` → build: `assets/css/app.css` (committed build output so PHP can enqueue without requiring Node on the server)
- Content globs: theme `*.php`, `woocommerce/**/*.php`, `inc/**/*.php`, `assets/js/**/*.js`
- Map existing tokens (`--sc-color-*`, fonts, `--sc-gutter`, `--sc-content-max`, `--sc-bp: 1024px`) into Tailwind `@theme`
- Keep Google Fonts enqueue as today; do not duplicate font loading in CSS

## Implementation steps

1. **Scaffold build tooling in the theme**
   - Add `wp-content/themes/still-cup/package.json` with `tailwindcss` + `@tailwindcss/cli` (or equivalent v4 CLI).
   - Scripts: `build` (once), `watch` (dev). Document in theme README or `vibe-coder/resource/ui/still-cup/`.
   - Add `.gitignore` only for `node_modules`; **commit** the built CSS so staging/prod do not need Node.

2. **Create Tailwind entry + theme tokens**
   - `assets/src/css/app.css`: `@import "tailwindcss";` plus `@theme { ... }` mirroring `theme.json` / `:root` in `main.css` (page, primary, surface, hero, story, border, summary, muted, sand, olive, chalk; Newsreader/Inter; content max 1312px; breakpoint 1024px; touch 44px).
   - Expose useful aliases (e.g. `bg-page`, `text-primary`, `font-display`, `font-body`, `max-w-content`) so templates stay readable.
   - Import residual component CSS after Tailwind layers (`@import` or `@layer components`) so specificity stays controlled.

3. **Enqueue strategy**
   - Replace separate `still-cup-main` + `still-cup-templates` with a single built `still-cup-app` handle pointing at `assets/css/app.css` (fonts remain a dependency).
   - During migration, either (a) `@import` existing `main.css` + `templates.css` into the Tailwind entry until migrated, or (b) enqueue built Tailwind first then legacy files — prefer **(a)** so one file ships and purge still sees utilities used in PHP.
   - Bump `STILL_CUP_VERSION` when the built CSS changes.

4. **Migration policy (what to convert now vs later)**
   - **Now:** Wire pipeline end-to-end; prove one low-risk surface uses utilities (e.g. supporting `page.php` shell or a simple Home section) without visual drift.
   - **Now:** Document AI conventions: prefer utilities for spacing/layout/type; keep/extend `sc-*` for multi-state Woo widgets (swatches, cart tables, checkout columns) when a component class is clearer.
   - **Later (out of scope unless time allows):** Gradual replacement of large blocks in `templates.css` / `main.css`; do not delete working component CSS until the matching markup is converted and smoke-tested.
   - Do **not** strip Woo layout CSS via dequeue unless overrides already cover floats/columns (existing theme already fights Woo CSS — keep that behaviour).

5. **PHP / markup conventions for AI**
   - Prefer Tailwind in new markup; when editing existing `sc-*` blocks, either leave classes + CSS alone or convert the whole block in one pass (avoid half-migrated sections).
   - Dynamic classes (PHP conditionals) must appear as complete class strings in source so the scanner can see them (avoid runtime-constructed class name fragments).
   - Keep accessibility: focus-visible, ≥44px touch targets, ≥16px inputs — encode as reusable component classes or documented utility recipes in UI docs.

6. **Docs & catalog**
   - Update `vibe-coder/resource/ui/still-cup/` with Tailwind setup, token → utility map, and “when to use `sc-*` vs utilities”.
   - Optional: short skill note under `vibe-coder/resource/skills/wordpress/` if agents need a reusable Still Cup Tailwind recipe.

## Notes & Decisions

- **Preflight:** Tailwind’s reset can fight WordPress/Woo markup. If forms or lists break, disable or scope preflight (`@import "tailwindcss/theme" "tailwindcss/utilities"` without preflight, or layer overrides) rather than rewriting all Woo templates.
- **theme.json** remains the WP editor palette source; keep colours in sync with Tailwind `@theme` manually (same hex values as today).
- Feature-003 templates stay the visual source of truth; this feature is tooling + convention, not a redesign.
- Catalogue / shipping / payments remain out of scope (unchanged from feature-003 notes).
- If Node tooling is undesirable long-term, a follow-up could vendor a one-shot CI build; for now local `npm run build` + committed CSS is enough.
